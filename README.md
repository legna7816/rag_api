# RAG API (검색 증강 생성 서비스)

노트북에서 실험한 RAG(임베딩 검색 + LLM 생성)를 실제 호출 가능한 API로 구현하고, FAISS 벡터 인덱스와 Docker/CI-CD까지 적용한 프로젝트.
"RAG가 뭔지 배우는 단계"에서 "서비스로 만들어 운영하는 단계"까지 다뤘다.

## 사용 기술
- Python, FastAPI, Docker, GitHub Actions
- 임베딩: `jhgan/ko-sroberta-multitask`
- 생성 모델: `Qwen/Qwen2.5-1.5B-Instruct` (CPU 추론)
- 벡터 검색: FAISS (`IndexFlatIP`)

## 구조
```
HTTP 요청 → FastAPI → FAISS 벡터 검색 → 프롬프트 구성 → LLM 생성 → JSON 응답
```

## 진행 과정

### 1. RAG 파이프라인 구현 → FastAPI로 API화
- 노트북에서 검증한 검색(Retrieval)+생성(Generation) 로직을 `/ask`, `/search` 엔드포인트로 구현
- 모델 로딩은 서버 시작 시 한 번만 실행되도록 설계 (요청마다 로딩하면 응답에 수십 초 소요)

### 2. Docker 컨테이너화
- 모델을 빌드 시점에 미리 다운로드해 이미지에 포함 → 컨테이너 실행 즉시 서비스 가능
- `--host 0.0.0.0` 설정으로 컨테이너 외부에서 접속 가능하도록 구성

### 3. GitHub Actions CI/CD
- push 시 자동으로 문법 검사(`test` job) → Docker 빌드 검증(`docker-build` job) 실행
- ML 특유의 제약: 모델 로딩·추론은 CI에서 생략(시간/비용 문제), 문법 검사만 수행

### 4. FAISS 벡터 인덱스 적용
- 브루트포스(전체 순회) 방식에서 FAISS 인덱스로 전환
- 인덱스를 파일로 저장/로드하도록 구현해 서버 재시작 시 재임베딩 불필요
- `POST /documents`로 서버 재시작 없이 지식 베이스에 문서 동적 추가 가능

### 5. 실제 공공데이터 적용 (식약처 레시피 DB)
- 장난감 문서 대신 식약처 조리식품 레시피 DB(1,156건)를 실제 데이터로 사용
- API JSON → 자연어 문서로 변환하는 전처리 파이프라인 구축 (한국어 조사 자동 처리 포함)

## 핵심 실험 & 발견

### RAG의 효과 — hallucination 감소
같은 질문("RAG는 뭐야?")을 RAG 있을 때/없을 때로 비교:

| 조건 | 결과 |
|---|---|
| RAG 사용 | 정확한 정의 답변 |
| RAG 미사용 | 존재하지 않는 용어로 완전히 지어낸 답변 |

### RAG의 한계 — 거짓 정보 주입 테스트
검색 문서에 의도적으로 틀린 정보를 넣었을 때:
- 수학처럼 절대적 사실(예: "1+1=3")은 모델이 스스로 거부
- 역사·문화 등 암기 기반 지식은 검색된 거짓 정보를 그대로 따름

→ **결론: RAG는 검색된 문서 품질에 의존하며, LLM이 오류를 자동으로 걸러줄 것이라 기대하면 안 된다.**

### 프롬프트 엔지니어링 디버깅 — 위치 실수의 영향
실제 레시피 데이터 적용 중, 시스템 지시문을 프롬프트 템플릿이 아닌 사용자 질문(`question`) 필드에 잘못 넣었을 때 답변이 완전히 붕괴하는 것을 확인. 지시문과 사용자 질문의 역할을 코드 상에서 명확히 분리해야 함을 실전에서 확인.

### 모델 크기별 안정성 비교
같은 프롬프트, 같은 레시피 데이터로 두 모델을 비교:

| 모델 | 특징 |
|---|---|
| Qwen2.5-0.5B | 응답 빠름(10~20초), 답변 거부·형식 붕괴 종종 발생 |
| Qwen2.5-1.5B | 응답 느림(30초~1분), 안정적이고 일관된 형식 유지 |

→ 작은 모델일수록 프롬프트 지시를 안정적으로 따르지 못하는 경향을 직접 확인. 모델 크기와 응답 속도·안정성 사이의 트레이드오프를 실측함.

### FAISS 성능 특성
- `IndexFlatIP`(정확한 인덱스)는 소규모 데이터(문서 1~10만 개 수준)에서 numpy 브루트포스 대비 유의미한 속도 이점이 없음을 실측으로 확인
- 진짜 성능 이점은 `IndexIVFFlat` 등 근사(ANN) 인덱스가 대규모(수십만~수백만) 데이터에서 발휘됨을 이해
- → 도구 도입이 무조건 성능 개선으로 이어지지 않으며, 데이터 규모에 맞는 선택이 필요함을 확인
